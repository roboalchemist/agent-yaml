The task tree

The value of task: is a nested list and mapping structure. The shape decides what runs in order and what runs at the same time. Nothing else schedules work.

One rule list versus mapping

A list runs its items in order. A mapping runs its keys at the same time. Lists and mappings nest freely, so a tree can sequence a fan-out and then fan back in.

List sequential

directory: /tmp/tree-demo
cli-agent: opencode

task:
  - setup:
      prompt: "Create the work directory"
  - build:
      prompt: "Write build.txt"
  - publish:
      prompt: "Write published.txt"

Mapping parallel

directory: /tmp/tree-demo
cli-agent: opencode

task:
  - review:
      stats:  {prompt: "Write stats.md"}
      report: {prompt: "Write report.md"}

Each runs setup, then build, then publish in the first case, and stats beside report in the second. A dry run prints which is which:

[Sequential Step 1]
    Task: review
      [Parallel Group - 2 tasks]
        Task: stats
          [Task]
            Prompt: Write stats.md
        Task: report
          [Task]
            Prompt: Write report.md

A mapping only means parallel when it sits where a task definition is expected. The value of a top-level task: must be a list.

Entries and meta fields

Every list item is one named task: a mapping with a single key (the name) whose value is the task definition. That definition is either a leaf (it has a prompt or a loop) or another mapping of child tasks.

Meta fieldEffect
promptMakes the task a leaf. The text goes to the agent CLI.
loopMakes the task a loop leaf, repeated per item. Takes precedence over prompt.
taskA nested list of child tasks, run in order.
includeNames from the top-level includes, appended to the prompt.
validateValidators run after the task exits 0.
retrymax-attempts and on-validation-failure.
skip-ifFile check evaluated before the task runs.
whenExpression gate. An empty string skips the task.
envEnvironment variables for this task.
directoryWorking directory for this task, relative to the workflow directory.
cli-agent-configAdapter options for this task.
on-errorfail, continue, or skip for this task.

Any other key in a task definition is a child task name. That is why the parallel example above needs no parallel: keyword.

A task with a prompt is a leaf. Sibling keys next to that prompt are ignored, not executed. This passes validation and silently drops the child:

directory: /tmp/tree-demo
cli-agent: opencode

task:
  - parent:
      prompt: "Write parent.txt"
      child: {prompt: "Never runs"}

Nesting

Lists and mappings alternate. This example sequences three phases, runs two workers inside the middle phase, and sequences two follow-ups inside a nested task: list.

directory: /tmp/tree-demo
cli-agent: opencode

task:
  - prepare:
      prompt: "Write plan.md"

  - execute:
      collect: {prompt: "Write data.csv"}
      analyze: {prompt: "Write analysis.md"}

  - publish:
      task:
        - checksum: {prompt: "Write checksums.txt"}
        - index:    {prompt: "Write index.md"}
1prepareseqWrite plan.md
2executepar
collectWrite data.csv
analyzeWrite analysis.md
3publishseq
checksumWrite checksums.txt
indexWrite index.md

Execution order: prepare, then collect and analyze together, then checksum, then index.

Loops as nodes

A task definition with a loop is a leaf that repeats. It participates in the tree like any other node, so a loop can be one branch of a parallel group.

directory: /tmp/tree-demo
cli-agent: opencode

task:
  - prepare:
      prompt: "Write rows.csv with a name column"

  - process:
      docs: {prompt: "Write overview.md"}
      rows:
        loop:
          type: csv
          source: "/tmp/tree-demo/rows.csv"
          workers: 4
        prompt: "Summarize {{loop.item.name}} into /tmp/tree-demo/out/{{loop.item.name}}.md"

Here docs and rows run together. The loop expands into one task per CSV row, with up to four rows in flight.

What validation accepts checked with the CLI

ShapeResultMessage or note
task: [ name: {prompt}, ... ] accepted Sequential list of named tasks.
name: {a: {prompt}, b: {prompt}} accepted Parallel group. Keys become tasks.
name: {task: [ ... ]} accepted Nested sequential list inside a task.
task: [ {prompt: "..."} ] rejected Task definition for 'prompt' ... must be a dict, got str. List items need a name.
name: {task: {a: {prompt}}} rejected Task at ... must be a dict, got str. Use a list under task:.
name: {} rejected Task with neither prompt nor nested tasks.

Failure behavior

Inside a list, a failing task stops the list when on-error is fail. Later items never start. With continue the failure is logged and the next item runs. With skip the run proceeds and the failure is not counted.

Inside a mapping, tasks are already submitted to the thread pool when the first one fails. Pending tasks are cancelled and tasks already running finish. The run still exits non-zero.

That is the limit of cancellation. A parallel group is not an atomic unit.

Where it lives

execute_task_tree in agent_yaml/cli.py is the interpreter. It branches on three cases: a list runs in order, a dict with loop is a loop leaf, a dict with prompt is a leaf, and anything else is a parallel group.

agent_yaml/validator.py enforces the shapes above before anything runs. agent_yaml/graph.py projects the same tree into the node graph used by agent-yaml serve, so the picture in the visual runner is the tree you wrote.
